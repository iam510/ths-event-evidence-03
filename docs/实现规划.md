# 第三题实现规划：投资事件情报与证据时间线

规划日期：2026-10-30。状态：题目已阅读，尚未开发、运行、测试或部署。本文中的功能、案例和技术选择均为计划，不代表已经完成。

## 1. 题目理解与交付边界

本地第三题对应原题编号「题目 08」，时限为 24 小时。目标是帮助用户判断：一件投资事件最早从哪里出现，后续哪些事实发生变化，证据之间有什么冲突，现在能够确认什么，以及与关注公司的关系。

产品的核心不是生成新闻摘要，而是完成可操作的闭环：

> 输入一条新材料 → 识别事件及具体主张 → 与已有证据比较 → 合并、另建或待确认 → 更新主张状态 → 显示变化原因及原文依据。

所有源码、可提交数据、文档及验证材料放在本目录内，解压后不依赖相邻的 01、02 文件夹。仅打包目录仍不足以满足原题：最终 README 必须填写实际可访问的 Web URL 与源码仓库 URL。远端账号、仓库可见性及部署平台在实际发布阶段按用户授权确定，本次规划不创建远端资源。

## 2. 产品范围与用户任务

目标用户：需要持续跟踪少量公司事件、核对消息变化的个人投资研究用户。使用构造的关注列表，不接入真实持仓。

首版聚焦公司公告、公开新闻及明确标记的观点/传闻。用 2–3 个资料可追溯的事件展示产品；并用单独标记的构造材料覆盖否认、更正、过期等不易齐全取得的场景。真实案例数量以资料核验结果为准。

一次完整体验：

1. 从关注公司进入事件列表，看到当前状态、关键变化、最新披露时间和数据新鲜度。
2. 打开事件，查看「当前可确认事项 / 待核实事项 / 冲突事项」及对应证据。
3. 在时间线上展开材料，查看原文摘录、来源链接、四类时间和来源之间的引用关系。
4. 粘贴一段新材料，填写来源、披露时间等元信息，点击分析。
5. 查看系统建议归属的事件、提取的主张及依据；歧义时选择合并、另建或保留待确认。
6. 提交后看到结论的前后变化及原因，刷新页面仍可回到本次演示记录。

不纳入首版：全网实时爬取、大规模推荐、行情预测、买卖建议、真实持仓分析、复杂账号权限、多用户协作。

## 3. 页面与交互

优先完成一个工作台，避免扩展大量页面：

| 区域 | 内容 | 主要操作 |
| --- | --- | --- |
| 事件列表 | 公司、事件标题、状态、最新变化、更新提示 | 搜索公司、筛选状态、切换事件 |
| 事件详情 | 当前判断、未决问题、公司关系、依据与限制 | 展开每条结论的证据 |
| 证据时间线 | 公告/新闻/观点/传闻、版本关系、时间字段 | 切换排序、筛选类型、查看原文 |
| 新材料面板 | 正文、来源、链接、已知时间 | 分析、确认归属、提交更新 |
| 变化记录 | 哪条主张变化、变化前后、触发证据 | 回看更新前的判断 |

界面必须显式显示加载、空结果、分析失败、来源不可访问、时间缺失和记录保存失败。失败时保留用户输入，允许重试，不将失败显示成正常处理完成。

## 4. 事件、主张与证据建模

最小数据对象：

- **事件**：主体公司、相关方、事件类型、对象、时间范围、标题和关联主张。
- **主张**：可被独立核对的一件事，例如「双方已签署协议」或「交易金额为 10 亿元」。一篇材料可以包含多个不同类型的主张。
- **证据**：材料原文、发布者、来源链接、原文定位/摘录、内容指纹、时间字段、引用来源及支持/反驳的主张。
- **关系**：转载自、更新了、更正了、否认了、支持或反驳。更正和否认必须指向具体材料或主张。
- **结论版本**：当时采用的证据、规则版本、主张状态、变化理由及生成时间，保留历史，不直接覆盖。
- **标的关系**：公司在事件中是主体、交易对方、被明确披露的关联方，还是模型推断的潜在关联方；每种关系均须附依据。

### 事件识别与合并

先按主体、对象、事件类型和时间范围生成候选，再由模型判断是否属于同一事件并说明依据。阈值和候选规则通过样例校准，不把模型自报的置信度当成事实。

同公司不同项目、同项目不同阶段、标题相似但主体不同，均需专门测试。证据不足时保持待确认；有用户确认入口和操作记录。重复材料不重复入库，多家转载同一原始消息不计作多份独立佐证。

### 信息类型与证据权重

按主张区分事实陈述、观点、推测、传闻，并保留分类依据；「事实陈述」表示内容的表达类型，不自动等于已经证实。来源类型与内容类型分开，新闻或公告也可能包含预测和观点。

首版使用可解释的高/中/低证据权重，依据包括原始性、对该主张的直接程度、可核验性、来源独立性和适用时间。权重不是真实性概率，也不直接按媒体数量投票。缺失或无法核验的来源降级并提示原因。

### 当前状态与版本变化

状态以具体主张为单位，事件层面汇总关键主张，避免一个字段代表全部真相：

| 新情况 | 计划行为 |
| --- | --- |
| 仅有传闻 | 标记待核实，不输出已发生的事实结论 |
| 出现直接证据 | 更新对应主张，并附支持依据与适用范围 |
| 公司否认 | 标记存在否认，展示否认范围及原文；不能自动宣判客观事实已被彻底推翻 |
| 来源更正金额/日期 | 更正对应字段，旧值保留历史，其他无关主张继续保留 |
| 两个直接来源相互矛盾 | 标记证据冲突并展示双方，不强行消解 |
| 有效期结束或长期无新信息 | 显示适用期结束/信息陈旧及规则依据，不推导为事件为假或已取消 |
| 旧消息被重新转载 | 保留原始披露时间，不以新抓取时间制造新进展 |

## 5. 四类时间与可追溯性

- 事件发生时间：材料描述的实际发生时间，可以为空、区间或「尚未发生」。
- 披露时间：来源发布材料的时间，保留时区与精度；未知时不以抓取时间冒充。
- 抓取/录入时间：系统实际接收这份材料的时间。手工输入明确标注为录入。
- 更新时间：材料版本实际更新的时间；系统结论更新时间另外记录，避免混淆。

默认按披露时间展示证据，可切换发生时间。缺失字段明确标注；时间精度不同、先披露后发生、晚录入旧材料均要能解释。原始来源的精确首发无法核实时，只称「当前已收录材料中的最早来源」。

每条核心结论可以打开对应主张、原文摘录、来源链接和时间。出现数字时保留原值、单位、币种、口径和材料日期；不清楚时展示缺失，不补造。关系推断需标记推断及推导依据，不能把行业关联写成已签合同或已获订单。

## 6. AI 与确定性逻辑分工

AI 负责：材料中的主体和主张提取、内容分类、候选事件匹配建议、支持/反驳关系建议，以及有证据引用的文字摘要。

程序负责：结构校验、必填项与引用检查、原文片段核对、材料去重、时间处理、主张版本和结论重算、存储及错误状态。来源权重不由模型任意生成；状态按已验证的证据关系和规则计算。关系有歧义时不自动升级结论。

模型输出采用结构化格式；无效字段、无法定位的引文、模型超时或调用失败须拦截，允许重试。无模型配置时，内置样例可展示已有结果，但新材料分析明确不可用；不能用硬编码结果冒充 AI 实时分析。

首版不需要模型自主浏览任意网页。用户提交的正文仅作为待分析材料，不能改变系统指令；即使原文要求给出买卖建议，也不能改变产品边界。

## 7. 数据接入与技术方案

原题优先数据源为扶摇与 iFinD。当前工具清单未发现这两类专用调用工具；本次通过网页读取两处入口均未取得有效文档内容（不可访问/超时）。这不能证明服务不可用，也不能证明已获得数据权限。

实施第一步应核对：是否已有合法凭证、是否具备新闻/公告原文和历史更新时间字段、调用限额、缓存及再分发权限。扶摇是否适合该题须按实际字段判断，不为展示接口而增加无关行情。

- 若可接入：优先接入其中一个能提供事件原文证据的来源，保留接口字段到页面证据的映射。
- 若暂时不可接入：先使用允许公开引用的原始公告/新闻链接及必要摘录，提供手工材料导入；README 如实说明覆盖率与刷新方式。
- 构造材料使用虚构公司与显著标记，单独作为测试/演示，不混入真实事件。受限数据不进入提交包或公开仓库。

建议采用 TypeScript 的前后端一体 Web 应用，模型调用放在服务端，配结构化校验和可替换的数据适配层。具体框架、模型、依赖版本和托管平台在实施时核对环境后确定，本次不声称任何平台已可用。

存储要求先明确再选型：公开样例只读；用户新增材料在演示会话内隔离，支持刷新恢复与重置；部署环境必须有适配的持久化方式，不能假设临时文件系统可保存记录。API Key 仅在服务端环境变量中，提交 `.env.example` 占位模板。

## 8. 24 小时执行顺序

以下为工作预算，不代表已经开始计时；实际起止按收到题目的时间计算。

| 预算 | 工作 | 阶段验收 |
| --- | --- | --- |
| 0–2 小时 | 核对数据/模型/部署能力，选择案例，确定数据结构 | 至少一个合法可用的证据输入路径，已知时间和来源可核对 |
| 2–6 小时 | 实现材料入库、主张提取、候选匹配、确认归属 | 新材料确实进入同一事件或另建事件，重复材料可识别 |
| 6–10 小时 | 实现证据关系、权重、时间与版本重算 | 更正/否认/冲突能改变对应主张并保留历史 |
| 10–15 小时 | 完成事件工作台与完整操作链路 | 用户能从公司进入事件、导入材料并追溯变化依据 |
| 15–19 小时 | 异常、合规、边界与浏览器验证 | 失败可见、错误不污染结论、真实与构造资料可区分 |
| 19–22 小时 | 部署，核对线上持久化与外部访问 | 在新会话实际完成主链路，记录 URL 与仓库版本 |
| 22–24 小时 | 整理交付文档、检查提交包、可选录屏 | 解压后可依 README 运行，必交项有真实结果 |

进度不足时先减少案例、筛选项和视觉装饰，保住新材料导入、事件归属、证据追溯、结论变化、异常处理和线上访问。演示视频最后安排。

## 9. 验收与测试计划

| 场景 | 关键预期 |
| --- | --- |
| 传闻 → 相关方表态 → 正式公告 | 状态随证据变化，能够回看每次变化依据 |
| 同公司不同项目 | 不误合并；歧义可人工确认 |
| 重复导入与多站转载 | 不重复计数，不虚增独立证据权重 |
| 更正交易金额与单位 | 当前值采用更正值，旧值保留在历史，原文可核对 |
| 部分否认与证据冲突 | 只影响对应主张，不覆盖整起事件 |
| 时间缺失、乱序录入、历史转载 | 显示缺失并正确区分披露/发生/录入/更新 |
| 到期与陈旧 | 明确提示范围与依据，不自动判假 |
| 空输入、超长输入、无效模型输出 | 可解释地拦截或报错，保留输入，不写入错误结论 |
| 数据或模型接口失败 | 不生成正常结论，保留上次结论并标注其时间和本次失败 |
| 引用不存在、正文含恶意指令 | 拦截无依据输出；原文指令不能改变系统行为 |
| 请求涨跌预测、收益承诺、买卖建议 | 不生成违规结论，保持事实核对任务 |
| 刷新、重置、不同演示会话 | 记录按设计恢复或隔离，公开样例不被污染 |

验证分三层：规则与版本逻辑的自动化测试、真实模型/数据接口的联调记录、部署后浏览器实际操作。构造数据通过不等于真实接口通过；文档中分别记录。保留关键步骤截图或可重放测试输入，但不能只以截图证明功能可用。
